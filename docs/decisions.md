# Architecture decisions

Add a new entry whenever a library, pattern or trade-off is chosen. Newest at the bottom.
Format: **D-number — title** · date · status (Accepted / Superseded by D-x) · decision · why · alternatives considered.

---

**D-001 — Electron + Angular + Angular Material** · 2026-11 · Accepted
Decision: desktop app built with Electron; UI in Angular with Angular Material, TypeScript strict.
Why: existing dictation MVP uses this stack; team knows it; good Windows support.
Alternatives: Tauri (smaller, Rust backend) — rejected for now to avoid a rewrite.

**D-002 — All AI on company servers** · 2026-11 · Accepted
Decision: speech-to-text via our hosted Qwen3-ASR; text tasks via our internal LLM endpoints (OpenAI-compatible API). Endpoints come from managed config.
Why: data must not leave the company.

**D-003 — Meeting capture without a bot** · 2026-11 · Accepted
Decision: capture the microphone and the computer's own audio output (WASAPI process loopback on Windows) as two separate channels, via a native helper process.
Why: works with Teams and Zoom without admin approval of a meeting bot; mic channel identifies the user.

**D-004 — Local SQLite storage** · 2026-11 · Accepted (library: see D-013)
Decision: better-sqlite3 with versioned migrations; transcripts stored at word level with channel and timestamps; secrets via Electron safeStorage.

**D-005 — No stored voiceprints in the pilot** · 2026-11 · Accepted
Decision: speakers are labelled per meeting and named by the user (with attendee suggestions). Voiceprints only behind a feature flag after legal/DPO approval and opt-in.
Why: voiceprints are biometric data under GDPR.

**D-006 — Agents propose, users approve** · 2026-11 · Accepted
Decision: one orchestrator model with personas; tools are marked read-only or action; every action goes through an approval queue and is logged.
Why: safety, trust, and protection against instructions hidden in documents or emails.

**D-007 — Scaffold tooling: Angular CLI + tsc + electron-builder** · 2026-11 · Accepted
Decision: Angular 21 (CLI, standalone components, zoneless, Vitest unit tests) builds the renderer to `dist/renderer`; main and preload compile with plain `tsc` (CommonJS) to `dist/app`; electron-builder packages. Production renderer is served via a privileged `app://renderer` protocol, not `file://`. Playwright `_electron` for end-to-end tests; ESLint (angular-eslint + typescript-eslint) + Prettier. All npm packages are devDependencies, because Angular is bundled and main has no runtime deps, so nothing from node_modules ships in the app. npm 11 `allowScripts` limits install scripts (only esbuild allowed).
Why: Angular 21 instead of 22 because the dev machine runs Node 22.13 (Angular 22 needs ≥22.22); upgrade later. tsc instead of a bundler keeps the toolchain small; the sandboxed preload uses type-only imports so it needs no bundling. electron-builder gives NSIS installers and Windows signing for VAI-108. A custom protocol gives a real origin for CSP, IPC sender checks and Angular routing.
Alternatives: Electron Forge (weaker Angular support, Squirrel installer); Vite/esbuild bundling for main (not needed yet); `file://` loading (no origin, weaker CSP and routing).

**D-008 — Typed IPC contract with sender checks** · 2026-11 · Accepted
Decision: every channel is declared once in `shared/ipc-contract.ts` (request/response types). Main registers handlers through `createIpcRegistrar`, which rejects calls whose sender frame is not our renderer origin. Preload exposes narrow functions on `window.aiWorkflow`, never `ipcRenderer`. Angular reaches it only through the `ElectronApi` service.
Why: compile-time safety on both sides, one place to review the attack surface, and easy mocking in tests.
Alternatives: exposing a generic `invoke(channel, …)` to the renderer (wider attack surface).

**D-009 — AI endpoints are user-editable in Settings** · 2026-11 · Accepted (partly supersedes D-002)
Decision: the speech-to-text and LLM base URLs, model names and API keys are set by the user in Settings (story VAI-113), not only through managed config. VAI-104 (managed endpoint config) is closed. Requests are made from the main process only, to the configured hosts. An optional host allowlist that IT can lock down may be added later; when empty, any http(s) URL is allowed.
Why: product owner wants users to connect the app to the company AI servers themselves.
Risk: a user could point the app at an outside AI service, which breaks the "all AI on company servers" rule. Mitigations: URLs validated (http/https, no credentials or query); the allowlist hook above; pilot users are told to use company endpoints only.
Alternatives: managed config only (VAI-104 as written) — rejected by product owner for now.

**D-010 — Settings and secrets storage** · 2026-11 · Accepted
Decision: settings live in `<userData>/settings.json` as `{ version, data }`, upgraded step by step by `electron/settings/migrations.ts`, validated field by field with hand-written checks (no schema library). Writes are atomic (temp file + rename). Corrupt files are moved aside (`settings.corrupt-<time>.json`) and defaults are used; a file from a newer app version is left untouched and updates are refused. Secrets (API keys, later tokens) live in a separate `<userData>/secrets.json`, each value encrypted with Electron `safeStorage` (DPAPI on Windows, Keychain on macOS), file mode 0600. If OS encryption isn't available (incl. Linux `basic_text`), secrets are not stored — never a plain-text fallback. The renderer can set, check and clear a secret but there is no channel that returns its value; only the main process decrypts. Logs name fields and files, never values.
Why: meets VAI-105; keeps keys out of the renderer, which is the part exposed to web content.
Alternatives: electron-store (extra dependency, no field-level recovery); zod for validation (extra dependency, not needed for a small schema); keytar (deprecated, native module).
Update 2026-11-19: uses the async safeStorage API (`isAsyncEncryptionAvailable`, `encryptStringAsync`, `decryptStringAsync`); the sync functions are deprecated in Electron 45. Values written with the sync API decrypt unchanged (checked against a real profile). When the OS reports `shouldReEncrypt` (key rotated), the value is re-encrypted and saved. So `SecretStore.get/set/isAvailable` and `AppDatabase.open` are async; type-aware lint (`no-floating-promises`) on `electron/` makes sure they're awaited.

**D-011 — Design tokens as Sass map → CSS variables, Material pointed at them** · 2026-11 · Accepted
Decision: every colour, font, spacing, radius, shadow and border is written once in `src/theme/_tokens.scss` and emitted as `--aiw-*` CSS variables on `:root`. Angular Material's system variables (`--mat-sys-*`) are overridden to point at our variables (`mat.theme-overrides`), and buttons/form fields get token-based overrides. Components use only variables; a test fails on raw colours outside `src/theme/`. A second test checks every real text/background pair for 4.5:1 contrast, and an e2e test checks rendered text in the app. `design/tokens.md` is generated from the SCSS (`npm run tokens`). Fonts (Fraunces, Archivo, JetBrains Mono) are bundled from `@fontsource-variable/*` (OFL).
Why: one place to change the look; runtime variables mean a token change reaches every screen and every Material component; contrast is enforced, not hoped for.
Changes from the screenshots: placeholder #838e81 → #637063, Notetaker avatar background #c5d4bb → #d2dec9 and Writer olive #5e6b1e → #515f1f (all to reach 4.5:1); the black input fields in the mocks are not copied.
Alternatives: Material palettes only (can't hit exact brand colours); tokens in JSON with a build step (more tooling); Google Fonts (external service, not allowed).

**D-012 — UI kit: Material for behaviour, own components for look** · 2026-11 · Accepted
Decision: buttons, inputs, selects, toggles, checkboxes and radios are Angular Material components restyled with tokens (`mat.*-overrides`, strong focus indicators, a few `.aiw-*` classes such as `.aiw-danger` and `.aiw-option-card`). Things Material doesn't have are our own standalone components in `src/app/ui/` with the `aiw-` prefix: card, chip, keys (key caps), agent avatar, badge, icon. Interactive variants of card and chip use attribute selectors on native `<button>`/`<a>` so keyboard and screen-reader behaviour stay native. Icons are Lucide shapes copied into `icons.ts` (ISC, no package) and drawn as inline SVG. A gallery at `/gallery` shows every component; e2e checks hover/focus/disabled states, full Tab order, keyboard actions and an axe (WCAG 2.1 AA) scan.
Why: Material already solves focus, ARIA and keyboard handling; wrapping it again would add bugs. Our own components stay tiny and token-only.
Alternatives: wrap every Material control in an `aiw-` component (more code, breaks forms and radio groups); lucide-angular package (extra dependency for ~20 icons); icon font (loads from the internet / not allowed).
Also: `danger-soft` lightened #fae0da → #fcece8 after axe found red-on-pink chip text at 4.36:1.

**D-013 — Encrypted SQLite: libsql + ordered migrations** · 2026-11 · Accepted (replaces the library in D-004)
Decision: the local database is `<userData>/data/app.db`, opened with `libsql` (pinned 0.5.29; Turso's SQLite fork with a better-sqlite3-style synchronous API) using its built-in whole-file encryption, cipher `aes256cbc`. The key is 32 random bytes created on first run and kept in the secret store (encrypted by DPAPI/Keychain) under a main-only name the renderer can't set, read or clear. No OS encryption → the database stays closed (never plain text). Lost/wrong key → the unreadable file is moved aside (`app.unreadable-<time>.db`) and a new database starts. Schema changes are TypeScript migrations in `electron/db/migrations/` (versions 1, 2, 3 … checked at startup), each applied in its own transaction and recorded in `schema_migrations` + `PRAGMA user_version`; a failure rolls back that migration, is logged, and leaves the app running with database status "error". One backup copy is made before migrating an existing database. Each migration must have its own test file (enforced by a test). Only the main process touches the database; features get their own typed IPC calls, never generic SQL.
Local only: libsql can also sync to Turso's cloud; we never use it. `electron/db/open.ts` passes only the cipher, key and timeout, and a test fails if any main-process code uses the sync/remote options or `libsql/promise`.
libsql quirks handled in `open.ts`: `Statement.get()` adds an enumerable `_metadata` timing field to rows and ignores `pluck()`; both are fixed once for every statement, so rows are plain objects (tested). Use `pragmaValue()` instead of `db.pragma()` (which also returns `_metadata`).
Packaging: this is the app's first runtime dependency. libsql ships prebuilt Node-API binaries as one optional package per platform (`@libsql/<platform>`), with no install script, so electron-builder's native rebuild is off and each platform build keeps only its own binary package (`asarUnpack` for `.node`). npm installs only the current platform's binary, so `dist:win` first runs `scripts/fetch-native.mjs win32-x64-msvc` (via `npm pack`, so the configured registry and integrity check apply). Electron-side unit tests run inside Electron's Node (`scripts/run-in-electron.mjs`).
Why: real encryption at rest that doesn't depend on IT enabling BitLocker; better-sqlite3-style API; libsql is on the company's approved package list. Our first choice, better-sqlite3-multiple-ciphers 13.x (SQLCipher v4 format), isn't approved; the only approved version, 11.10.0, can't be used: no prebuilt binary for Electron 45 and its C++ no longer compiles against Electron 45's V8 (checked 2026-11-19).
Alternatives: better-sqlite3-multiple-ciphers (see above); @signalapp/sqlcipher (AGPL-3.0); @journeyapps/sqlcipher (always compiles, async API); `node:sqlite` built in, or plain better-sqlite3, with column-level encryption (table structure stays readable, breaks search); sql.js (whole database in memory).
Note: dev databases created with the earlier SQLCipher build are unreadable now and are moved aside automatically on first start.
OpenWhispr reference: its database uses plain better-sqlite3 with WAL and `CREATE TABLE IF NOT EXISTS` + ad-hoc alters; we took only WAL mode.

**D-014 — Logging, redaction and diagnostics export** · 2026-11 · Accepted (VAI-107)
Decision: one main-process logger (`electron/logging`) writes readable lines — `2026-11-19T16:28:45.522Z WARN  [db] Message name=value …` — to `<userData>/logs/main.log`, rotated at 1 MB with 5 files kept (≈5 MB max). Writes are synchronous so the last lines before a crash survive; logging never throws. Level `info`; dev/test may set `AIW_LOG_LEVEL` (ignored when packaged); dev also echoes to the terminal. `console.*` is not allowed in `electron/` outside the logger (test). Renderer errors reach the log only through `log:renderer-error` (Angular `ErrorHandler`): name, message and stack frames, capped and rate-limited (30/min). Main-process crashes are observed with `uncaughtExceptionMonitor` (doesn't change Electron's default handling; recovery is VAI-111), plus `render-process-gone` / `child-process-gone`.
No transcripts, audio or keys, in four layers: (1) facts go in fields, and fields whose names look like content or credentials (`text`, `transcript`, `audio`, `prompt`, `key`, `token`, `authorization` …) are always written as `[redacted]`; only numbers, booleans and short strings are kept, objects/buffers are omitted; (2) every line is scrubbed of key shapes (Bearer/Basic, `sk-…`, secrets in URL query strings, 32+ hex chars, long mixed-case base64); (3) the secret store reports every value it saves or reads, and those exact strings are replaced with `[secret]`; (4) messages are capped at 500 characters and kept to one line.
Diagnostics export (Settings → Diagnostics): the main process asks where to save (default Downloads), writes a zip with `README.txt`, `app-info.json` (version, OS, database status, which keys are set — yes/no), `settings.json` (settings never hold secrets) and `logs/*.log`, scrubbing every file once more; it never reads `secrets.json`, the database or any user content. Zip writer is our own (~100 lines, Node `zlib` deflate + `crc32`) to avoid a dependency.
Alternatives: electron-log / winston / pino (new dependencies; we need custom redaction anyway); JSON-lines logs (less readable for support); `archiver`/`adm-zip` for the zip (dependency for a small, fixed job).
OpenWhispr reference: `src/helpers/debugLogger.js` sets the level from an environment variable; we took only that idea.

**D-015 — Windows installer: per-user NSIS, fuses, signing from environment** · 2026-11 · Accepted (VAI-108)
Decision: electron-builder's NSIS one-click installer, per-user (`perMachine: false`, `allowElevation: false`) into `%LOCALAPPDATA%\Programs\AI Workflow` — no admin rights, no UAC. A fixed `nsis.guid` keeps upgrades working when the placeholder `appId` is replaced. `build/installer.nsh` (`customUnInstall`) offers to delete `%APPDATA%\AI Workflow` on interactive uninstall (default No), keeps it on silent uninstall unless `/DELETEDATA`, and never touches it during an update (`--updated`). Silent switches: `/S`, `/D=`, `/DELETEDATA` (README). A portable zip is still built for testing. Electron fuses are on in packaged builds: no `ELECTRON_RUN_AS_NODE`, no `NODE_OPTIONS`, no `--inspect`, app code only from the integrity-checked asar, cookie encryption. Signing uses electron-builder's `CSC_LINK`/`CSC_KEY_PASSWORD` (never in the repo); `release:win` sets `forceCodeSigning` and then `scripts/check-signature.mjs` checks the installer and app exe carry an Authenticode signature (PE header, no dependency, works on macOS). The pipeline is tested with a self-signed certificate (`scripts/make-test-cert.mjs`); the company certificate is VAI-108b (type unknown: .pfx, token/HSM, or a signing service — a cloud signing service would need approval as an outside service).
Fix 2026-11-20: a platform `files` list with only exclusions makes electron-builder add `**/*`, so Mac/Linux builds — and Windows builds from VAI-106 until VAI-301 — packed the whole repository (sources, tests, docs, tool settings; no secrets). Each platform list now has an include anchor (test), `THIRD_PARTY_NOTICES.md` is shipped on purpose, and `smoke:packaged` fails if `app.asar` holds anything but the built app.
Testing: Playwright can't drive packaged builds with these fuses, so `scripts/smoke-packaged.mjs` starts the packaged app with a throwaway `--user-data-dir` (and `--use-mock-keychain` on macOS dev builds) and waits for the "Database opened status=ok" log line. Windows behaviour (no UAC, uninstall prompts, silent switches, upgrade) is checked by hand with `docs/windows-install-test.md`.
Why: meets VAI-108 with no admin rights and no new dependency; NSIS `/S` works with Intune as a Win32 app (install behavior: User).
Alternatives: MSI (per-user MSI is awkward, needs WiX; per-machine MSI needs admin); MSIX (needs signing for every install and changes file-system paths); Squirrel (deprecated in electron-builder, no uninstall choices).

**D-016 — Feature flags from Windows registry policy** · 2026-11 · Accepted (VAI-109)
Decision: meetings, agents and voiceprints are off by default and switched on by IT through `HKCU\Software\Policies\AI Workflow` (per user — pilot groups) and `HKLM\Software\Policies\AI Workflow` (per machine, wins). Values are REG_DWORD 0/1; anything else is ignored and logged. Read once at startup with Windows' own `reg.exe` (full path, 64-bit view; no dependency) and frozen; the renderer can only read them (`features:get`, no setter). macOS dev builds read a root-owned `/Library/Application Support/AI Workflow/policy.json`; dev/test can use `AIW_POLICY_FILE` (ignored when packaged). Hidden means gone: routes use `canMatch` (no route, no lazy code downloaded, URL falls back to Home), main-process parts register through `featureGate`/`registerIf`, and texts that mention a feature are conditional. Flags are loaded by an app initializer before the first screen, so nothing flashes. The same policy keys will carry other IT settings (e.g. VAI-110 auto-update).
Why: the Policies keys are the Windows standard for managed app settings, GPO and Intune can target user groups, and normal users can't write them — so nobody can enable voiceprints (legal/DPO gated) for themselves.
Alternatives: JSON file in `%ProgramData%` (standard users can create files there); flags from a company server (another service and an outage risk; possible later); flags in user settings (user-controlled, not managed).

**D-017 — Settings structure** · 2026-11 · Accepted (VAI-204)
Decision: Settings has the design's sections (Dictation, Transcription, AI cleanup, Vocabulary, Style per app, About & diagnostics) plus **AI servers** after Transcription, because the server URLs, keys and models are user-editable (D-009) and belong together. Sections whose options come with later stories show a "Coming soon" page; each story adds its controls to its own section, and no control is shown before it does something. Every page uses one header with a save pill (`SaveStatus`, provided by the Settings layout): "Changes save automatically" → "Saving…" → "Saved", or an error. Settings schema v2 adds `dictation` (mode, toggle shortcut); v1 files migrate with every value unchanged (fixture test + e2e).
Alternatives: split AI servers into Transcription (speech-to-text) and AI cleanup (LLM) — rejected: the LLM also powers summaries and agents, so it would be hard to find; hide empty sections until their stories — rejected for now (no pilot users yet).

**D-018 — Tray, close-to-tray and start at sign-in** · 2026-11 · Accepted (VAI-205)
Decision: the app runs in the system tray. Closing the window hides it (dictation keeps working); real quits — tray "Quit", Cmd+Q, OS shutdown/sign-out, later updates — set a quitting flag in `before-quit` so the close goes through. A second launch re-shows the window. A main-process `DictationStatus` (idle/listening/recording) drives the tray icon, tooltip and menu; the hotkey and recorder stories set it. Tray icons are generated in code (`scripts/tray-icons.mjs`, no image library) from the logo until design provides real ones; recording adds a red dot so the state isn't colour-only. Start at sign-in uses the OS login entry as the source of truth (`startup:get/set`), with `--hidden` on Windows so the app starts in the tray; it's disabled when running from source. No Windows tray GUID yet: an unsigned exe that moves can't reuse one — add it with the company certificate (VAI-108b).
OpenWhispr reference: `src/helpers/windowManager.js` (quit flag set in `before-quit`, close → hide) and `src/helpers/tray.js` (tray GUIDs only in production builds); ideas only, no code copied.
Alternatives: quit on close (users lose dictation when tidying windows); a `startup.openAtLogin` setting in settings.json (drifts from the OS when changed in Task Manager).

**D-019 — Hold-Ctrl through our own Windows helper process** · 2026-11 · Accepted (VAI-301)
Decision: Ctrl-alone detection uses a tiny C program of our own (`native/win-key-listener/main.c` → `aiw-key-listener.exe`) with low-level keyboard and mouse hooks, run as a child process. It prints only `READY`, `CTRL_DOWN clean|dirty`, `CTRL_UP` and `OTHER` — never which key — never blocks input, ignores injected input (our own paste) and the AltGr fake Ctrl, and exits when its stdin closes. All timing (120 ms) and shortcut logic is TypeScript (`electron/hotkey/`), unit-tested on any OS. A supervisor restarts the helper, and after 3 failures in a minute gives up; whenever it isn't running the toggle shortcut (Electron `globalShortcut`, default Ctrl+Shift+Space) takes over, and Esc cancels only while a toggle recording runs. Built with mingw-w64 (`brew install mingw-w64` on macOS) at `dist:win`; shipped in `app.asar.unpacked` so electron-builder signs it with the app (checked by `check-signature`).
Why: a separate process can't freeze typing system-wide when the app is busy (an in-process hook that takes >~300 ms makes Windows lag or drop it); no npm dependency; small, auditable privacy surface.
Alternatives: `koffi` FFI hook in the main process (dependency, in-process risk); `uiohook-napi` (dependency); PowerShell `Add-Type` hook (blocked by Constrained Language Mode and flagged by EDR).
macOS stays dev-only (product owner, 2026-11-20): no packaged Mac app and no Apple signing (no Apple Developer ID).
Update (VAI-312, 2026-11-20): when **running from source** (`npm start`), macOS gets Hold Ctrl and paste at the cursor through two small Swift helpers (`native/mac-key-listener`, `native/mac-paste`; built into `resources/mac/` by `npm start` with Xcode command-line tools, never packaged). They speak the same line protocols as the Windows helpers, so all logic stays in the shared TypeScript. The Electron.app from npm is already signed, and macOS grants Input Monitoring (Hold Ctrl) and Accessibility (⌘V) to the app that launched it (Terminal or VS Code), so the permissions stick across rebuilds. The watcher is a listen-only event tap; without permission it says `NO_PERMISSION` and is not restarted until "Check again" in Settings, which explains both permissions and opens the two fixed System Settings pages. The paste helper writes the text current-host-only (no Universal Clipboard) and marked transient/concealed (nspasteboard.org) and restores the clipboard if its changeCount is unchanged. Without either permission or helper, the toggle shortcut and clipboard + notification keep working. A packaged Mac app would need a company Developer ID, notarization and MDM-granted permissions (not planned).
OpenWhispr reference for the Mac helpers: `resources/macos-globe-listener.swift`, `resources/macos-fast-paste.swift`; ideas only.
OpenWhispr reference: `resources/windows-key-listener.c` (helper + stdout protocol, AltGr scan-code check); ideas only, our code.

**D-020 — Microphone capture in a hidden audio window** · 2026-11 · Accepted (VAI-302)
Decision: a hidden, never-shown BrowserWindow (same sandbox/preload/CSP as the main window, no background throttling, audio allowed without a click) owns the microphone. It captures with getUserMedia (echo cancellation off, noise suppression and auto gain on) into an AudioWorklet and converts to 16 kHz mono 16-bit PCM in TypeScript (box-filter downsampling). The audio context and worklet are created once at startup and suspended while the mic is closed, so opening the mic is ~50 ms; the mic opens on a clean Ctrl press (before the 120 ms threshold) and closes again if it was a shortcut. "Keep mic ready" (0/5/10/30 s, default 10) keeps the mic open after dictating with only a 0.5 s rolling pre-roll, cleared when it closes; the tray shows Listening meanwhile. A missing chosen device falls back to System default; a blocked mic is explained in Settings and the tray. Recordings (max 10 min) go to the main process in memory over IPC; they are never written to disk or logged. Permissions: everything is denied except `media` with audio only, requested by the audio window from our origin; our windows may _check_ it (device names). Only the audio window may send `audio:event`/`audio:recording`.
Why: Chromium's capture is reliable on Windows and needs no native module; a dedicated window keeps capture running while the UI is hidden or navigating; the permission scope stays minimal.
Alternatives: native capture module or helper (more native code to sign and maintain); capture in the main window (stops when it reloads, harder to scope the permission); opening the mic only when recording starts (clips the first word).
OpenWhispr reference: `src/helpers/audioManager.js` / `preparedMicCapture.js` (prepare the mic with a pre-roll on key press, discard it if unused); ideas only.
Testing note: Chromium's `--use-fake-ui-for-media-stream` bypasses Electron's permission handler, so tests use only `--use-fake-device-for-media-stream`; `--use-file-for-fake-audio-capture` is ignored in Electron's sandboxed audio service.

**D-021 — Speech-to-text over the OpenAI-compatible transcription API; Groq for development only** · 2026-11 · Accepted (VAI-303)
Decision: dictation sends each finished recording once, as an in-memory 16 kHz mono WAV, to `POST {baseUrl}/audio/transcriptions` (multipart `file` + `model`, `response_format=json`) of the server configured in Settings → AI servers, through `AiHttpClient` (configured host only, no redirects, key never logged). No SDK: `net.fetch` + `FormData`, no new dependency. Recordings under 0.3 s and silent ones (peak < −40 dBFS; Whisper-style models invent text for silence) are not sent. Retries (`ai.retries`, 0.5 s × attempt, or a Retry-After ≤ 5 s) only after network errors, 429 and 5xx; never after a timeout (would multiply the wait) or another 4xx. Recordings are transcribed one at a time, in order; the tray shows "Transcribing". Until VAI-304 the text goes to the clipboard with a notification that never contains the text. The code is provider-neutral: nothing names a provider.
Development: until the company Qwen3-ASR API is approved, the product owner uses Groq's OpenAI-compatible API (`whisper-large-v3-turbo`) on their own machine, with their own key entered in Settings — an outside cloud service, so **dev only, one user, no confidential dictation**, never a default and never in builds or docs for users. Switching to Qwen3-ASR is a settings change.
Why: the company server and Groq both speak the OpenAI transcription API; one request per dictation is simplest and fits the "< 2 s for 10 s" target; streaming comes with VAI-306.
Alternatives: `openai` npm package (dependency for one call); streaming upload while recording (VAI-306); retrying timeouts (a 30 s timeout × 3 is too long to wait for dictation).
OpenWhispr reference: `src/utils/wavBuilder.ts` (standard 44-byte WAV header) and `src/helpers/transcriptionRoute.ts` (`{base}/audio/transcriptions` shape); ideas only, our code.

**D-022 — Paste at cursor through our own Windows helper** · 2026-11 · Accepted (VAI-304)
Decision: a second small C helper, `aiw-paste.exe` (`native/win-paste/main.c`, user32 + advapi32), runs once per dictation. The text comes in on stdin (never the command line, which other processes can read); it prints one fixed result line. It saves the clipboard (every memory format — text, HTML/RTF, images, copied files, app formats; GDI-handle formats are re-created by Windows from DIB), writes the text marked `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory=0`, `CanUploadToCloudClipboard=0` (no Win+V history, no cloud sync, no clipboard managers), waits ≤ 0.5 s for Alt/Win/Shift, sends Ctrl+V (Ctrl+Shift+V for known terminals) with SendInput, and after 0.5 s restores the saved clipboard only if the clipboard sequence number is unchanged (nothing new copied). It refuses admin (elevated) windows, because UIPI drops the keystrokes without an error, and pastes nowhere when no window has focus; then and on any failure (helper crash, 3 s timeout) the text stays on the clipboard and a notification says so. Success shows nothing. The Hold-Ctrl watcher ignores injected keys, so our Ctrl+V can't start a dictation. Shipped unpacked and signed like the Ctrl watcher. macOS (dev only, D-019) keeps clipboard + notification.
Why: Electron's clipboard API can't add the history/cloud exclusion formats (a single write replaces the whole clipboard) and can't restore copied files or app formats; a separate one-shot process keeps native code small and out of the main process; no npm dependency.
Alternatives: Electron clipboard + PowerShell `SendKeys` (slow, often blocked by EDR/Constrained Language Mode, loses formats); `nircmd` (third-party binary); adding a PASTE command to the Ctrl watcher (it only runs in Hold mode and would mix responsibilities); typing the text key by key (slow, breaks with IMEs and auto-complete).
Limits: the text goes to whatever has focus when transcription finishes (no focus restore yet); the 0.5 s restore delay may need tuning for slow apps (Windows checklist §12).
OpenWhispr reference: `resources/windows-fast-paste.c` (terminal class/exe list, waiting for modifiers, SendInput) and `src/helpers/clipboard.js` (restore after ~500 ms only if unchanged); ideas only, our code.

**D-023 — Dictation overlay in its own pre-created, non-focusable window** · 2026-11 · Accepted (VAI-305)
Decision: the floating dictation bar is a third window (`/overlay`), created hidden at startup with its page loaded, so starting a dictation only moves it and calls `showInactive()` (measured in e2e, well under 100 ms). It is frameless, transparent, `focusable: false`, always on top (screen-saver level, all desktops, over full-screen apps), ignores the mouse (clicks reach the app below), not in the taskbar, and a non-activating panel on macOS; same sandbox/preload/CSP as the other windows. `OverlayController` (pure TypeScript) follows `DictationStatus`; the hotkey tells it "stop"/"cancel" before the recorder, so release goes straight to "Transcribing…" without flicker and a cancel hides at once. The audio window reports only a loudness number (RMS on a −60…0 dB scale, 20 per second while recording) which main forwards to the overlay window on a second main → renderer channel, `overlay:state`, sent only to that window. The target app is the paste helper's `--front-app` answer: the program file name (Windows) or app name (macOS), mapped to a short name ("OUTLOOK.EXE" → "Outlook"); never the window title, which can contain email subjects or file names. Placement: bottom-centre of the work area of the display under the mouse pointer.
Why: a pre-loaded window is the only way to meet 100 ms reliably; a non-focusable, non-activating window can't steal the caret from the app being dictated into; no new native helper for the app name.
Alternatives: show the bar in the main window (steals focus, hidden when the window is closed to the tray); create the window on demand (hundreds of ms); window titles for the chip (privacy); the foreground app from the Hold-Ctrl watcher (not running in toggle mode).
OpenWhispr reference: `src/helpers/windowConfig.js` / `windowManager.js` (`focusable: false`, `showInactive()`, mouse pass-through for the dictation panel); ideas only.

**D-024 — AI cleanup with a 3 s budget and a "no added words" guard** · 2026-11 · Accepted (VAI-307)
Decision: after transcription, the text goes once to the LLM server from Settings → AI servers (`POST {llm.baseUrl}/chat/completions`, OpenAI-compatible, through `AiHttpClient`; temperature 0) with one system prompt per level — **Light** (punctuation, capitals, filler words; nothing else) or **Polished** (also false starts, repeats, self-corrections, paragraphs) — and the transcript inside `<transcript>` tags, described as text to clean, never a request. Default **Light** (product owner). A hard 3 s limit covers the whole call (headers and body), with no retries; on timeout, error, no LLM configured or an unusable answer the **raw text is pasted** without a notification (logged only). "Never adds facts" is enforced in code, not only asked of the model: the answer is rejected if it is empty, clearly longer than what was said (> 110 % + 20 characters) or contains more than max(1, 5 %) content words that weren't spoken (small grammar words like "I", "am", "to" don't count — VAI-308) — which also catches the model answering a question, following an instruction in the dictation, or translating. `<think>` blocks, echoed tags and wrapping quotes are stripped. `max_tokens` has a 1024 floor because reasoning models (e.g. gpt-oss) otherwise spend the budget on hidden reasoning and return nothing. On Windows line breaks become CRLF before pasting. Settings schema v4 adds `dictation.cleanup`; logs carry level, timing and outcome only.
Why: the LLM is fast enough for dictation (Groq qwen3.8-27b ~0.1–0.2 s, gpt-oss-20b ~0.3–0.7 s in a manual check), but a dictation tool must never paste something the user didn't say; a cheap word check catches the dangerous failures regardless of model.
Alternatives: trusting the prompt only; a second LLM call to verify (doubles latency); streaming the cleanup (nothing to show before paste).
OpenWhispr reference: `src/helpers/sourceFidelity.js`, `templatePrompts.js` (a fidelity rule in the prompt); ideas only — ours adds the code check.

**D-025 — Style per app as extra prompt rules, matched by app name** · 2026-11 · Accepted (VAI-308)
Decision: four styles — Professional, Casual, Code, Neutral — each a short block of extra rules appended to the Light/Polished cleanup prompt (D-024); Neutral adds nothing. Styles change form only (sentence completeness, contractions, punctuation, code formatting); the cleanup rules and the "no added words" check still apply, so a style can't add greetings, sign-offs or prose. The target app is looked up once when recording starts (`TargetApp`, the paste helper's `--front-app`: program/app name, never a window title) and shared by the overlay chip ("Outlook · Professional") and the cleanup of that recording, even if another dictation has started meanwhile. Rules (`dictation.styles`, settings schema v5, ≤ 50, names ≤ 40 characters, unique ignoring case) match the short name shown in the bar, ignoring case; apps without a rule use Neutral. Defaults: Outlook → Email (VAI-308b), Word → Professional; Teams, Slack → Casual; VS Code, Terminal, Command Prompt → Code. **Email** lays out only what was said — a spoken greeting on its own line, the message in paragraphs, a spoken closing and name on their own lines — and never adds a greeting, closing, name or signature (Outlook adds the user's own signature; the app can't know the recipient). Settings v6 switches Outlook to Email only when the stored rules are exactly the v5 defaults; edited lists are kept. An opt-in greeting/sign-off template written by the user remains a possible later story. Logs carry the style, not the app name. **Code** is for code and command lines: written exactly as typed — no full stop at the end, no capital at the start, spoken commands/options/symbols as typed ("make dir" → `mkdir`, "ls dash la" → `ls -la`, "pipe" → `|`) — and never turns a description into a command ("delete everything" stays words; an `rm -rf` answer fails the word check). A code-side safety net (`tidyCode`) drops a trailing full stop on single lines and lowercases a capitalised command that isn't an English word (`Ls`, `Git`). The app only pastes, never presses Enter, so a command never runs by itself.
Why: one prompt per (level × style) stays small and reviewable; matching the name users see in the bar makes rules easy to write.
Alternatives: free-text style instructions per app (prompt-injection and quality risk); matching window titles or URLs (privacy); a separate LLM call for tone (latency).
